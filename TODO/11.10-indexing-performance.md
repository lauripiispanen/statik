### 11.10 Indexing performance: SQLite batch operations (S)
**Complexity**: S
**Prerequisites**: none
**Files**: `src/cli/index.rs`, `src/cli/db.rs`

**The problem**: Indexing 7,228 files (98K symbols, 138K references) takes ~15s,
and 65% of that time is SQLite overhead from individual INSERT/DELETE statements.

**Profiling breakdown**:
- `clear_file_data`: 33.5% (~5s) — 5 DELETEs × 7,228 files = 36K individual DELETEs
- `insert_symbol`: 17.5% (~2.6s) — 98K individual INSERTs
- `insert_reference`: 14.3% (~2.1s) — 138K individual INSERTs
- `insert_import`: 1.2% (~0.2s)
- Parsing (parallel): 24.1% (~3.6s)
- File discovery: 8.5% (~1.3s)

**Quick wins** (in priority order):

1. **Skip `clear_file_data` on `--force`** (free 33.5%)
   On `--force`, the DB is deleted and recreated (index.rs:34-36), then every file
   goes through `clear_file_data` which runs 5 DELETE statements against empty
   tables. These DELETEs are pointless on a fresh DB — there's nothing to clear.
   Fix: skip `clear_file_data` when the file is new (not previously indexed).

2. **Use prepared statements** (reduce INSERT overhead)
   `insert_symbol`, `insert_reference`, etc. each call `conn.execute()` per row,
   which re-prepares the SQL statement every time. That's ~250K statement
   preparations. Fix: use `conn.prepare_cached()` or `conn.prepare()` once and
   reuse the statement handle across all inserts.

3. **Batch DELETEs for incremental re-index**
   For incremental re-indexing of changed files, the 5 individual DELETEs per file
   could be replaced with a single batch `DELETE FROM symbols WHERE file_id IN (...)`
   for all changed files upfront, instead of 5 × N individual DELETEs.

**Bonus** (lower priority):
- `Node::parent()` calls in the Java parser (3.9%) — `maybe_extract_identifier_reference`
  and `maybe_note_static_class_reference` spend most of their time in
  `tree_sitter::Node::parent()`. Caching the parent or passing it during tree walk
  would help, but this is a smaller win.

Tasks:
- [ ] Skip `clear_file_data` for files not previously in the DB (covers `--force` case)
- [ ] Use `prepare_cached` (or prepare-once) for `insert_symbol`, `insert_reference`,
  `insert_import`, `insert_export`
- [ ] Batch `clear_file_data` DELETEs: collect changed file_ids upfront, run one
  `DELETE FROM X WHERE file_id IN (...)` per table instead of per-file
- [ ] Benchmark before/after on a large project (target: ≥50% reduction in indexing time)

**Acceptance**: Indexing the same 7K-file project drops from ~15s to under 8s.
`--force` reindex should be close to incremental speed since clear_file_data is skipped.
